# 拾年 / CHRONA 开发规范

本文档用于约束后续 AI 和开发者对当前 Flutter 项目的修改。目标是保持现有结构和视觉语言，避免重复实现、过度设计和无关重构。

## 1. 基本原则

每次修改遵循：

```text
先理解现有代码
→ 搜索是否已有实现
→ 优先复用
→ 最小范围修改
→ 完成后验收
```

具体要求：

- 修改前先搜索现有 Widget、Service、Provider、Model 和工具方法。
- 能复用已有实现时，不重新创建同类组件或工具函数。
- UI 优先使用 Flutter / Material 官方组件。
- 功能优先使用项目已经存在的依赖和成熟 API。
- 小功能不引入大型依赖、第二套状态管理或第二套导航方案。
- 不擅自增加当前任务之外的产品功能。
- 不修改与当前任务无关的代码、页面或数据库字段。
- 不为了“更完整的架构”进行无必要的大规模重构。
- 如果发现与当前任务无关的问题，只记录问题和影响，不顺手修复。

## 2. 当前架构边界

项目保持简单的分层关系：

```text
Screen / Widget
→ Provider
→ Database 或 Service
```

当前主要职责：

| 模块 | 当前职责 |
| --- | --- |
| `TaskProvider` | 任务加载、添加、编辑、完成切换、排序和删除 |
| `FocusProvider` | 当前页面内的专注 / 休息计时状态和生命周期 |
| `FocusSessionProvider` | FocusSession 加载、保存、笔记更新和统计数据来源 |
| `JournalProvider` | 按日期加载、保存和修改 JournalEntry |
| `FocusSettingsProvider` | 休息时长的 SharedPreferences 读写 |
| `AppDatabase` | SQLite 表结构、迁移、CRUD 和导入事务 |
| `NotificationService` | 本地专注 / 休息结束通知、权限和取消操作 |
| `DataTransferService` | JSON 文件选择、编码和设置恢复 |

除非当前任务明确要求，不主动引入：

- Clean Architecture；
- UseCase 层；
- Repository Interface / Impl 套娃；
- 新状态管理框架；
- 复杂依赖注入框架；
- 自定义后台常驻服务；
- 与现有 Provider 并行的另一套数据流。

如果当前代码已经形成统一模式，后续修改必须遵循该模式，而不是为单个页面创建新范式。

## 3. Widget 复用

```text
单页面单次使用
→ 页面内部实现

多处重复且结构稳定
→ 抽取公共 Widget
```

复用规则：

- 已有 `BrandHeader`、`ChronaBottomNavigation`、`PrimaryButton`、`LoopingDurationPicker` 等组件时优先复用。
- 已有页面内样式只出现一次时，不为了几十行简单 UI 单独新建文件。
- 新增公共 Widget 前，先确认至少有两处真实使用场景，或确实需要统一交互行为。
- 公共 Widget 的抽取不能改变已有页面的尺寸、颜色、间距和点击行为，除非任务明确要求统一调整。
- 图标优先复用 Material Icons，不新增自制 SVG、Canvas 或图片图标来替代已有语义图标。

## 4. Provider 与状态

- 一个 Provider 负责一个清晰业务领域，不把任务、日记、统计和设置混成一个 Provider。
- UI 不直接调用 SQLite；数据库读写通过 `AppDatabase`，页面通过 Provider 或当前已有 Service 访问。
- 页面临时状态可以留在 StatefulWidget，例如 Tab、输入框、选中日期、弹窗草稿和页面局部 loading。
- 不把所有短生命周期 UI 状态都搬进 Provider。
- 不在 `build()` 中执行数据库写入、文件操作、通知调度或其他重型副作用。
- 异步操作需要处理 loading、失败和页面销毁后的 mounted 状态。
- 防止重复保存、重复导入和重复创建计时器；优先复用现有的 `_isSaving`、`_isTransferring` 和 Provider 状态保护。
- `FocusProvider` 是当前活动计时器的内存状态，不要把它误当成持久化的 FocusSession。
- 计时页面返回、后台恢复和页面重建时，先确认当前 Provider 的所有权和生命周期，再决定是否创建或销毁实例。

## 5. SQLite 与数据变更

当前数据库通过 `AppDatabase` 管理，应用数据库版本为 `9`，包含 `task`、`focus_session`、`journal_entry` 和 `daily_question` 四张表。内置每日问题 JSON 只读存放在 assets，不导入 SQLite。

任何数据库变更必须：

- 明确提升 schema version。
- 在 `onUpgrade` 中提供按旧版本顺序执行的 migration。
- 保留旧用户数据，不能用删库重建代替迁移。
- 明确字段的可空性、默认值和历史数据回填规则。
- 保持 ID、时间、逻辑关联和备份字段含义一致。
- 多表覆盖、批量写入或需要原子性的操作使用 SQLite transaction。
- 不擅自增加外键、索引、表或字段；先确认当前业务是否需要。
- 不直接删除用户数据。删除数据必须属于明确需求，并说明是否影响关联历史记录。

当前 `focus_session.task_id` 是逻辑关联，不是 SQLite 外键；除非任务明确要求，不要自行加入级联删除。

导入恢复必须遵循当前策略：覆盖四张业务表、保留可用 ID、在事务中完成删除和插入；不要擅自改成合并导入。

## 6. 时间与日期

统一使用项目已有工具和存储约定：

| 场景 | 约定 |
| --- | --- |
| SQLite 时间点 | Unix epoch 毫秒，使用 `INTEGER` |
| SQLite 日记日期 | `YYYY-MM-DD` 字符串 |
| SQLite 时长 | 秒，使用 `INTEGER` |
| 本地日期归一化 | 使用 `startOfLocalDay()` / `startOfDay()` |
| 本地时间比较 | 需要按用户日期展示时先使用 `toLocal()` |
| 日期显示 | 优先使用 `formatFocusDate()`、`formatFocusDayHeading()` |
| 小时统计 | 优先使用 `formatFocusHoursDecimal()`，保留两位小数 |
| 时分显示 | 优先使用 `formatFocusTime()` |

业务展示格式统一为：

```text
M月D日 · 星期X
```

当前 `formatFocusDate()` 的实际输出是中点两侧无空格的紧凑形式 `M月D日·星期X`。新增代码仍应复用该 formatter，不要在页面内自行拼接另一种格式；如果要调整空格，应集中修改格式化入口并统一验收。

不要：

- 用不同单位保存同一类时间；
- 在不同页面重复实现星期、日期或时长格式化；
- 用 Flutter ticker 的执行次数代替真实计时；
- 把本地日期和 UTC 日期混用而不说明转换点。

## 7. UI 规范

所有新页面和明显的 UI 修改必须遵循：

[`docs/006.UI与交互规范.md`](./006.UI与交互规范.md)

至少保持：

- 黑 / 白 / 灰的视觉层级；
- 大留白、低信息密度和列表优先；
- 不擅自加入渐变、大面积彩色、大阴影或重卡片；
- 优先使用已有按钮、导航、品牌头部、输入框和图标风格；
- 数据有影响的操作提供确认、保存中状态或失败反馈；
- 文字 Tab 不改成胶囊式 SegmentedButton，除非任务明确要求；
- 统计、日期和时长遵循现有格式化函数。

如果设计稿、任务文字和当前代码冲突，先指出冲突和影响，再按任务范围做最小修改，不要顺手重做整页。

## 8. AI 修改要求

每次 AI 修改项目时，交付前至少说明：

1. 准备修改或已经修改了哪些文件。
2. 搜索并复用了哪些现有实现。
3. 本次只完成了哪些明确任务。
4. 哪些后续需求没有提前实现。
5. 如何验证本次修改。
6. 发现了哪些不属于本次任务的问题。

执行边界：

- 不提前实现后续需求。
- 不擅自修复无关代码或重命名无关文件。
- 不修改数据库 Schema、备份格式或公共 UI，除非任务明确包含这些范围。
- 不用“顺便整理”为理由扩大变更范围。
- 如果必须扩大范围，先说明原因、影响文件和不可避免的副作用。

## 9. 完成前检查

提交修改前确认：

- 变更文件只属于当前任务范围。
- 新代码没有重复已有工具或 Widget。
- Provider、数据库和 Service 的职责没有交叉污染。
- 日期、时间和时长没有新增第二种格式。
- 数据写入有错误处理，必要时使用 transaction。
- UI 遵循 `006.UI与交互规范.md`。
- 已按 [`009.测试与验收.md`](./009.测试与验收.md) 执行相关人工验收。
